# Post-Stage 19 总体审查与后续需求池

> 日期：2026-07-04  
> 性质：全局审查与候选需求池，**不是可直接执行的阶段需求文档**。后续要开发时，必须按 `docs/00_docs_management_standard.md` 拆成新的 Stage 文档，并先更新 `roadmap.md` / `CLAUDE.md` 阶段状态。

## 1. 审查结论

当前项目已经具备 AI 客服 Agent 的后端主闭环：聊天主链路、意图识别、槽位/任务状态机、确认门、ActionExecutor 写入口、RAG/FAQ、商品库、人工接管、鉴权、多租户、可观测、Langfuse、内容安全、WS/CSAT、知识库运营、成本控制、A/B 实验、多语言输出地基均已覆盖。

从工程结构看，核心边界基本合理：FastAPI route 主要做接入，业务编排在 Service + LangGraph 节点，Repository 负责数据访问，写操作没有绕过确认门和 ActionExecutor 的明显路径。`ruff`、`mypy`、全量 `pytest` 当前可通过。

但这还不是完整可上线产品形态。主要缺口集中在真实系统联调、运营前端、多渠道入口、多语言输入理解、多模态、运维看板与合规治理。另有若干文档状态漂移和监控口径冲突，需要在后续阶段前收口。

## 4. 建议拆分的后续候选阶段

### Stage 20：真实业务系统联调与工具生产化

目标：把 mock/MCP 示例服务替换为真实业务系统能力，保证读写工具可审计、可幂等、可补偿。

范围：订单查询、物流查询、售后工单、取消订单、改地址、发票等工具；外部幂等键；超时和重试；外部错误码映射；工具结果回查；联调验收数据。

不做：前端工作台、多渠道入口。

### Stage 21：坐席工作台与知识库运营前端

目标：让人工接管和知识库运营可被真实运营团队使用。

范围：坐席队列、工单详情、认领/回复/解决、上下文移交包展示、CSAT 查看；知识库草稿/审核/发布/回滚、FAQ 管理、命中率/盲区页面。

不做：新增 Agent 决策能力。

### Stage 22：多渠道接入层

目标：统一微信/企微/APP SDK/邮件等渠道进入同一聊天主链路。

范围：Channel Adapter、渠道消息标准化、签名验签、重试去重、渠道用户映射、附件元数据、主动消息回推。

不做：多模态理解本身，只接文本和附件占位。

### Stage 23：多语言输入理解与跨语言知识库

目标：补齐非中文用户的意图识别、槽位抽取、护栏与知识检索能力。

范围：语言检测、多语言训练集、多语言 intent eval、多语言槽位规则、多语言护栏词表、跨语言 query rewrite、知识库 locale 字段与检索策略。

不做：大规模人工翻译后台。

### Stage 24：多模态客服能力

目标：支持图片/语音进入客服链路。

范围：语音 ASR、图片 OCR、订单截图识别、商品图识别、附件安全扫描、结构化结果进入现有 SlotExtractor/IntentClassifier。

不做：视频实时客服。

### Stage 25：运营与合规治理

目标：补齐生产运营所需的权限、审计、数据生命周期和成本治理。

范围：角色细分、审计查询、数据保留/删除、租户成本报表、Grafana 看板、告警规则、实验配置管理、质量回流任务编排。

不做：改变主聊天决策链路。
