# Stage 35 需求：身份核验分级（Identity Assurance Level）

> 来源：roadmap 3.7 第二项（外部评审第十项采纳）。核心问题：查询订单/
> 改地址等功能不能只依赖「知道订单号」——不同敏感度的工具应要求不同的
> 身份保证等级，未达标结构性拒绝而不是靠提示词自觉。

---

## 1. 等级定义与工具声明

| 等级 | 含义 | 当前推导 |
|---|---|---|
| IAL0 | 未核验 | — |
| IAL1 | 渠道身份基本确认 | API Key 鉴权通过的渠道（`AUTH_ENABLED` 下有凭证）|
| IAL2 | OTP / 账户验证 | **暂无渠道**——要求 IAL2 的工具未达标转人工核实 |
| IAL3 | 高风险二次验证 | 预留（导出个人数据类） |

工具最低等级声明进**工具目录**（post-27 单一事实来源，readonly 先例的
第二次应用）：`ToolMeta.min_ial`——政策类查询 IAL0；订单/物流/会员等
涉个人数据的读 IAL1；写操作 IAL1 起，**改地址 IAL2**（改收货地址是
账号盗用的典型攻击面，评审示例采纳）。

## 2. 运行时推导与执法点

- 等级经 contextvar 注入（tenant budget 先例）：`chat_service` 入口按
  鉴权态解析——`AUTH_ENABLED` 且凭证通过 → `IDENTITY_LEVEL_AUTHENTICATED`
  （默认 1）；开发模式 → `IDENTITY_DEFAULT_LEVEL`（**默认 2 = 零回归**：
  沙盒互信，现有改地址 e2e 流程不变；生产按需下调到 1，改地址即要求
  IAL2 → 转人工，硬门槛由配置激活）；
- **执法点两处，结构性不可绕**：
  1. `ActionExecutor`（写）：invoke 前校验，未达标返回
     `IDENTITY_REQUIRED`——action_execute 回身份核实话术 + 建单
     （reason=IDENTITY_VERIFY → Case POLICY_REVIEW）交人工核实；
  2. `tool_invoke`（读）：未达标不调用工具，回核实话术（同建单）。
- LLM/诊断 agent 无豁免：诊断白名单工具都是读，等级校验在 provider
  调用前统一生效。

## 3. 红线

1. 等级校验是结构执法不是提示词约定（模型任何输出都绕不过）；
2. OTP 类凭证（未来接入）**不入日志不入决策留痕**（脱敏纪律延伸）；
3. 人工与 AI 权限不混用：坐席操作走 admin scope API，不经聊天工具链。

## 4. 验收

1. 目录声明齐全（每个工具有 min_ial，测试锁定）；
2. 等级不足：写操作被 executor 拒绝（不触发防重放消耗）、读操作不调用
   工具，均回核实话术并建单；
3. 默认配置零回归（沙盒 IAL2 互信，全量测试不变）；
4. 等级达标路径行为与之前完全一致。

## 5. 遗留

1. OTP/账户验证渠道（真实短信/账号体系接入后 IAL2 可达）；
2. 越权查询防护的业务侧（订单归属校验需真实订单系统的属主字段）；
3. IAL3 工具（导出个人数据）随真实合规需求。
